### 2、摘要

SomatoSync 面向医疗级全身运动障碍量化追踪：12 个可穿戴 IMU 节点经自研 ESP-NOW TDMA
＋自适应跳频协议无碰撞汇聚到网关，再经以太网上送 ROS 2 完成骨架重建与 AI 康复评估，
覆盖脑卒中、帕金森等 6 类病种。本作品把该系统两块自研 ESP32-S3 板卡适配到 openvela：
交付板级代码 1,284 行 / 16 个文件、两套 defconfig 与 1 个可复用 Skill；完成板级 bring-up、
引脚与供电时序、构建系统集成，并把 SSD1306 落地为 `/dev/lcd0` 标准 framebuffer，
满足大赛「至少落地图形 / AI / 多媒体之一」的要求。两个板型镜像均编译通过
（网关板 855,016 B、节点板 688,004 B），板级符号经核对确认已进入镜像；
节点板实测 text 647,730 B、data 11,740 B、bss 266,760 B。开发全程使用 AI Coding
（含小米 MiMo），累计消耗输入 117,891,569 tok、输出 4,610,068 tok。

### 3、正文

#### 3.1 绪论

**项目背景与问题定义**

运动功能障碍（脑卒中、帕金森、脑瘫、多发性硬化、骨关节术后、运动损伤）的临床评估，
长期依赖治疗师的主观观察与量表打分，存在**量化程度低、复诊间隔长、居家康复缺乏客观依据**
的问题。光学动捕精度虽高，但价格昂贵且必须在实验室内使用，无法覆盖居家场景。

本作品的应用场景是**康复科与居家康复的量化评估**：用可穿戴惯导方案替代光学动捕，
在真实生活空间中连续采集全身关节运动数据，为疗效评估与康复处方提供客观依据。

**技术难点**

1. **多节点 × 高频采样 × 无线无碰撞**：可穿戴方案的核心矛盾。ISM 频段拥挤，
   通用 CSMA 类 MAC 在高节点数、高上报率下丢包与延迟急剧恶化；医疗评估要求时序严格对齐，
   丢包会直接破坏关节角度的连续性。
2. **姿态解算的漂移与鲁棒性**：低成本 MEMS IMU 长时间积分必然漂移，
   需要在资源受限的 MCU 上完成可靠的融合与校准。
3. **在产品级硬件上完成操作系统适配**：本作品要适配的不是通用开发板，
   而是已量产的**自研网关板与可穿戴节点板**，外设组合、引脚分配与供电时序均需逐一还原，
   且板级配置的加载机制与大赛通用模板骨架并不一致（详见 3.2）。

**创新点**

1. **技术上**：用 TDMA 固定时隙从机制上消除上行碰撞，叠加自适应跳频（AFH）规避窄带干扰，
   并配合背压流控与无延迟丢弃策略保证时序连续性 —— 而非在 CSMA 上做退避调参。
2. **场景上**：把医疗级量化评估从实验室搬到居家场景，用可穿戴惯导替代光学动捕。
3. **交互上**：NFC「碰一碰」配网、OLED 状态菜单与五向键、触觉反馈，
   目标是让非技术用户（患者与家属）可独立完成佩戴与使用。
4. **工程上**：识别并修正了板级配置加载机制的关键差异 —— 见 3.2「方案论证与选型」。

#### 3.2 系统方案设计

**系统总体架构**

系统为五层技术栈，数据自下而上单向汇聚：

| 层 | 职责 | 承载硬件 |
| --- | --- | --- |
| 感知层 | 节点端双路 ICM-42688 高频 IMU 采集 | 可穿戴节点板 |
| 解算层 | 片内双 ESKF 姿态融合、双 IMU 在线校准 | 可穿戴节点板 |
| 传输层 | ESP-NOW TDMA 时隙调度 ＋ 自适应跳频 ＋ 背压流控 | 节点板 ↔ 网关板 |
| 汇聚层 | 以太网（W5500）转发、SD 卡原始数据落盘、OLED 状态显示 | 网关板 |
| 应用层 | ROS 2 上位机：UDP 桥接 → 正运动学 TF2 骨架 → 康复指标 → AI 报告 | 上位机（PC） |

数据流：节点 IMU 采样 → 片内 ESKF 解算 → 在分配的 TDMA 时隙内上报 → 网关按序汇聚
→ SD 卡落盘（原始数据可回溯）＋ 以太网上送 → 上位机骨架重建与评估。

**方案论证与选型**

1. **硬件平台选型（如实说明）**：大赛为每队发放的是 **ESP32-P4X-Function-EV-Board**
   （官方《支持的硬件平台》「二、待适配开发板」列表第 1 项）。经核查，openvela 当前
   **尚无 ESP32-P4 的芯片层支持**：`arch/risc-v/src/esp32p4` 与 `arch/xtensa/src/esp32p4`
   均不存在，`vendor_espressif/boards/` 下仅有 `esp32s3`。P4 的适配属于**从零开始的
   RISC-V 芯片层移植**（工具链与调试链路、启动流程、MMU、全部外设驱动均缺失），
   在本次提交周期内不可能完成。
   因此本作品将交付范围收敛为**已有芯片层支持的自研 ESP32-S3 板卡的板级适配**，
   并在此如实说明该取舍；ESP32-P4 的芯片层移植列为后续工作。
2. **参考基线选型**：适配以 `vendor_espressif/boards/esp32s3/esp32s3-eye` 为唯一可信基线
   —— 它是 openvela 官方已适配的 ESP32-S3 参考板，工程约定经过验证；
   而**不套用大赛模板中的通用占位骨架**。
3. **关键工程判断（本作品的重要发现）**：大赛模板把板级目录映射到
   `vendor/openvela/boards/`，但 ESP32-S3 的板级配置实际通过
   `CONFIG_ARCH_BOARD_CUSTOM_DIR` 机制定位，板目录**必须与芯片支持放在一起**
   （`vendor/espressif/boards/esp32s3/`），否则 Kconfig 与板级源码都加载不到。
   本作品据此修正了 manifest 的映射位置 —— 这一条若不修正，`make` 会直接找不到板级配置。
4. **端 / 云职责划分与降级策略**：本项目**不依赖云端**。全部数据采集、姿态解算与
   骨架重建均在本地完成，上位机仅承担可视化与报告生成。
   断网 / 弱网时系统**功能不降级**：网关将原始数据落盘至 SD 卡，网络恢复后可回溯补传；
   即网络仅影响「实时上送」，不影响「数据完整采集」。
5. **驱动策略**：W5500 以太网驱动在 NuttX 主线中已存在（`drivers/net/w5500.c`），
   本作品**不重写驱动**，只按 `struct w5500_lower_s` 契约提供板级 glue（SPI 总线、RSTn、INTn），
   既减少代码量，也保证后续可向上游提交。
6. **目标硬件符合本方向的范围界定**：本方向要求「选择一款**尚未适配 openvela 的硬件平台**」，
   并明确「**已适配的开发板不计入本赛道**」。本作品的目标硬件是**自研的 SomatoSync 网关板与
   可穿戴节点板** —— 两块板此前只跑过 ESP-IDF 固件、**从未适配过 openvela**，也不在官方
   《支持的硬件平台》「一、已支持开发板」清单内，因此符合本方向的要求。

   > 需要区分的是：ESP32-S3 的**芯片层**已由 openvela 支持（参考板 `esp32s3-eye`）。
   > 本作品**不重复做芯片移植**，工作量落在**板级** —— 板级 bring-up、外设组合与引脚/供电时序、
   > defconfig 与构建系统集成、硬件能力验证；这正对应本方向「适配参考范围」中的
   > 外设驱动适配、构建系统集成与硬件能力验证三项。

**关键模块设计**

1. **双核隔离**：Core 1 负责高频计算（采集与解算），Core 0 负责射频与网络；
   两核之间只用无锁原子原语通信，**禁止互斥锁**，避免高频路径被调度抖动打断。
2. **信标驱动（Beacon-driven）**：节点永远被动响应网关的 TDMA Beacon，不主动发起，
   从设计上消除上行竞争。多设备方案中，**网关板与节点板运行的是同一套 openvela 系统**，
   仅板型配置（`CONFIG_SOMATOSYNC_BOARD_GATEWAY` / `NODE`）与外设开关不同 ——
   即以「一套板目录 + 两套 defconfig」组织，而非两个独立板级目录。
3. **网关板外设组合**：W5500 以太网（SPI2）、PN5180 NFC（SPI3，配网）、
   SSD1306 OLED（I2C0，状态显示）、microSD（1-bit SDMMC，原始数据落盘）。
4. **节点板外设组合**：双路 ICM-42688 挂在**两条独立 SPI 总线**上（各带独立 LDO 使能，
   并注入外部 32.768 kHz 时钟以稳定采样时基）、SSD1306 OLED（带电源门控，帧间可完全断电）、
   DRV2605 触觉反馈、电池分压＋接地 MOS 门控（避免分压电阻长期漏电）。

#### 3.3 核心算法与技术原理

**AI 算法实现**

1. **端侧（节点板）—— 双 ESKF 姿态融合**：单个节点上两路 ICM-42688 分别做误差状态卡尔曼滤波
   （ESKF），再做融合与双 IMU 在线校准，抑制漂移。解算**全部在片内完成**，
   无线只上报解算结果而非原始采样，把带宽压力降到最低。
   选型理由：ESKF 相比四元数互补滤波在动态段精度更高，相比 EKF 数值更稳定且计算量可控，
   适合在无 FPU 加速的高频路径上运行。
2. **云端 / 上位的 AI 康复分析**：原系统由网关或上位机对时序数据做 AI 康复分析并生成报告。
   本作品交付的是**板级适配层**，该分析链路沿用原型实现，未在本阶段迁移到 openvela。
   （接口与鉴权方式见仓内 `docs/design/` 中原型设计说明；本阶段未启用云端模型调用。）
3. **说明**：本赛道（新硬件平台适配）的 AI 相关得分点集中在 3.6 的 AI-Native 开发说明，
   端侧 ESKF 与上述分析链路为系统既有能力，本作品未对其算法本体做改动 —— 如实说明。

**关键机制设计**

1. **TDMA 时隙调度**：网关周期广播 Beacon，为每个节点分配固定时隙；
   节点仅在自身时隙内上报，从机制上消除碰撞，而非依赖随机退避。
2. **自适应跳频（AFH）**：检测信道质量并规避窄带干扰，提升拥挤 ISM 频段下的鲁棒性。
3. **背压流控与无延迟丢弃**：当汇聚端处理不过来时，宁可丢弃过期帧也不排队，
   保证时序连续性 —— 医疗评估中「过期数据」比「没有数据」更有害。
4. **双核无锁 IPC**：跨核通信仅使用原子原语，避免互斥锁在高频路径上引入调度抖动。

**openvela 系统能力的深度运用**

本作品明确落地大赛三项核心能力中的 **图形**：

1. SSD1306 面板经 `board_lcd_initialize()` + `lcddev_register(0)` 注册为标准 NuttX LCD 设备，
   暴露 `/dev/lcd0`；
2. 使能 `CONFIG_LCD_FRAMEBUFFER` 后进一步成为标准 framebuffer，
   **LVGL 与 framebuffer 类 demo 无需改动即可运行**；
3. 面板内容对应真实系统功能：网关显示 TDMA 调度状态、节点在线数、存储状态；
   节点显示电量与姿态解算状态 —— 即原固件 OLED 菜单的 openvela 版本。

用到的 openvela / NuttX 组件：`drivers/lcd/ssd1306`、`drivers/net/w5500`、
`drivers/mmcsd`、`drivers/spi`、`drivers/i2c`、`esp32s3` 芯片层（GPIO / SPI / I2C / SDMMC /
Wi-Fi）、`nsh` 与 NSH builtin。

**对 openvela 的优化 / 拓展与改进建议**

1. 上游 `esp32s3-eye` 的 README 声称 `build.sh` 会自动应用 `esp-hal-3rdparty` 的
   spinlock 初始化补丁，**实测并非如此**（已 grep 全部 `.sh` / `.mk` / `Make.defs` / `CMakeLists`）。
   本作品把该补丁随仓提供为 `scripts/patches/0001-esp-hal-3rdparty-fix-spinlock-init.patch`，
   并在板级文档中写明应用时机。建议上游修正文档或在构建脚本中补上该步骤。
2. ESP32-S3 板级配置的加载机制（`CONFIG_ARCH_BOARD_CUSTOM_DIR`）与大赛通用模板骨架不一致，
   容易让新适配者走弯路。建议在上游或赛道指引中明确「ESP32-S3 板目录必须与芯片支持同目录」。
3. `task_tls_alloc` 依赖 `CONFIG_TLS_TASK_NELEM`，而 Wi-Fi 适配层会调用它，
   默认值下链接失败。建议在有 Wi-Fi 的板级 defconfig 中默认开启。

**软件 / 固件架构**

│   ├── somatosync_board_lcd.c # SSD1306 OLED（图形能力落地点）
│   ├── somatosync_board_eth.c # W5500 以太网板级 glue
│   └── somatosync_board_spi.c # SPI2/SPI3 状态查询（芯片层要求的板级钩子）

**数据流与关键流程设计**

openvela 启动时的板级挂接顺序：

```text
esp32s3_board_initialize()          [somatosync_boot.c]
        └─ 板级时钟 / 串口 / 控制台等芯片层初始化
board_app_initialize()              [somatosync_appinit.c]  ← BOARDIOC_INIT
        └─ somatosync_bringup()      [somatosync_bringup.c]
              ├─ board_lcd_initialize()      → SSD1306 → /dev/lcd0
              ├─ somatosync_w5500_initialize() → /dev/eth0
              ├─ SD 卡（SDMMC）注册
              └─ Wi-Fi / ESP-NOW 底层能力
nsh_main()                          [CONFIG_INIT_ENTRYPOINT]
```

关键设计：`somatosync_bringup()` 采用**单外设失败不阻断整板**策略 ——
任一外设初始化失败只记录错误并继续，保证板子仍能启动到 `nsh>` 控制台。
这使得「外设未焊接 / 未接线的板子」也能用于操作系统启动验证（见 3.5）。

**硬件设计与适配**

- **是否完成全新硬件平台适配或驱动开发：是。**
- **芯片 / 开发板型号**：ESP32-S3（模组 `ESP32-S3-WROOM-1`，4 MB Flash ＋ 8 MB Octal PSRAM）；
  适配对象为两块**自研板卡** —— SomatoSync 网关板与 SomatoSync 可穿戴节点板。
- **驱动类型**：板级 bring-up 与板级 glue（非通用驱动重写）。
  具体地：GPIO 引脚复用与供电时序、SPI2/SPI3 总线与片选、I2C0 总线、
  SDMMC 1-bit 模式、以及 SSD1306 / W5500 的板级接线与复位、中断引脚绑定。
  W5500 协议驱动复用 NuttX 主线实现（`drivers/net/w5500.c`），
  SSD1306 复用 `drivers/lcd/ssd1306`，本作品只提供板级 glue。

**驱动适配覆盖**（对应本方向评分加分项「适配的硬件平台覆盖范围越广、驱动越完整，
技术得分越高」）：

| 类别 | 本作品适配内容 | 落地形态 |
| --- | --- | --- |
| GPIO | 引脚复用、供电时序、复位与中断绑定、LDO 门控 | `board.h` 完整引脚映射（板型条件编译） |
| SPI | **两条独立 SPI 总线**（SPI2 / SPI3）、片选与总线参数 | W5500 挂 SPI2；PN5180 挂 SPI3；节点板双 IMU 分挂两条总线 |
| I2C | I2C0 400 kHz | SSD1306（地址 0x3C）、DRV2605 触觉驱动 |
| Display / LCD | SSD1306 128×64 注册为标准 LCD 设备 | `board_lcd_initialize()` → `lcddev_register(0)` → `/dev/lcd0`；开启 `LCD_FRAMEBUFFER` 后为标准帧缓冲 |
| Network（Ethernet） | W5500 板级 glue（SPI 总线、RSTn、INTn） | 复用主线 `drivers/net/w5500.c` → `/dev/eth0` |
| Storage | microSD，1-bit SDMMC 模式 | 芯片层 `board_sdmmc_initialize()` ＋ FAT |
| Wireless | Wi-Fi / ESP-NOW 底层能力接入 | 已接入；真机 panic（esp-hal 上游问题，见 3.5「已知问题」） |
| ADC / 电源 | 电池分压采样 ＋ 接地 MOS 门控 ＋ 独立 LDO 使能 | ADC1_CH1，避免分压电阻长期漏电 |
| NFC | PN5180 板级 glue（SPI3 ＋ BUSY/RST） | 协议栈列为后续工作 |
| 板级 SPI 钩子 | 芯片层要求的板级实现 `esp32s3_spi2_status()` 等 | `src/somatosync_board_spi.c` |

合计覆盖 **GPIO / SPI / I2C / Display / Network / Storage / Wireless / ADC 电源 / NFC
九类外设**，其中 SPI 为两条独立总线；网关板与节点板**各有一套完整 defconfig**。

- **适配难点与解决方案**：

| 难点 | 现象 | 解决方案 |
| --- | --- | --- |
| 板级配置加载机制与模板不一致 | 按模板路径放置板目录后，Kconfig 与板级源码均加载不到 | 改用 `CONFIG_ARCH_BOARD_CUSTOM_DIR`，板目录与芯片支持同目录（`vendor/espressif/boards/esp32s3/`） |
| `File Make.defs could not be found` | `configure.sh` 报错并中止 | `configure.sh` 解析 `${configpath}/../../scripts/Make.defs`，补板级 `scripts/Make.defs` |
| 工具链未进 PATH | `xtensa-esp32s3-elf-gcc: 未找到命令`，make 空转不产出 `.o` | `build.sh` 不会 source `build/envsetup.sh`，其通配也不匹配 `xtensa-esp32s3-elf`；改为显式 `export PATH=$PWD/prebuilts/gcc/linux-x86_64/xtensa-esp32s3-elf/bin:$PATH` |
| `LOCK_INITIALIZER_UNLOCKED` 初始化报错 | `error: invalid initializer` | esp-hal 克隆自 `main` 分支；应用 `0001-esp-hal-3rdparty-fix-spinlock-init.patch`（`0` → `SP_UNLOCKED`） |
| `undefined reference to esp32s3_spi2_status` | 链接失败 | 芯片层要求板级提供该符号，补 `src/somatosync_board_spi.c` |
| `undefined reference to task_tls_alloc` | 链接失败 | Wi-Fi 适配层调用该接口，补 `CONFIG_TLS_TASK_NELEM=4` |
| 节点板缺工作队列 | `#error Worker thread support is required (CONFIG_SCHED_WORKQUEUE)` | 节点板 defconfig 补 `CONFIG_SCHED_WORKQUEUE=y` |
| esp-hal 全量克隆反复中断 | 294 MB 克隆超时；`CHECK_COMMITSHA` 会 `rm -rf` 无分支引用的缓存 | `git init` ＋ `git fetch --depth=1 origin <sha>` ＋ 建分支 `keep`；并预置 `chip/esp-hal-3rdparty` 使 make 跳过克隆配方 |
| esptool 版本过低 | `Unsupported esptool version: 4.7.0 expects >= 4.8.0` | 升级 pip 后安装 `esptool`（5.4.0） |

**已知问题（如实说明，尚未解决）**

Wi-Fi 适配层在真机上触发 user panic：`EXCCAUSE=001c`（LoadProhibited），
经 `addr2line` 符号解析定位到
`esp-hal-3rdparty/components/wpa_supplicant/esp_supplicant/src/crypto/crypto_mbedtls.c:93`
的 `sha256_vector`（时间线：t=0.75 s OLED 初始化失败 → t=3.63 s Wi-Fi panic）。
该路径属 **esp-hal 上游无线适配层**，非本板级代码。
panic 后系统进入 halt，因此**当前镜像尚不能交付一个可交互的 `nsh>` 会话**。

配套说明：要让 openvela 在 ESP32-S3 上构建通过，除本仓已提供的
`scripts/patches/0001-esp-hal-3rdparty-fix-spinlock-init.patch` 外，还必须在 defconfig 中
显式给出 `CONFIG_XTENSA_TOOLCHAIN_ESP=y` 与 `CONFIG_STACK_USAGE_WARNING=0`
（二者被 `make savedefconfig` 当作默认值剥除；缺失时会分别导致构建回退到宿主 gcc、
以及生成非法 `-Wstack-usage=` 参数）。这两项已加入本仓两套 defconfig。

  与康复机构的数据服务合作。

  适配 openvela 后具备了接入更广泛 AIoT 生态与更多芯片平台的能力，
  有助于进一步降本与扩展产品线（如手环、手表形态）。
